⸻

Objective

Make Assistant widget CI checks semantically accurate.

An Assistant widget check must appear on a pull request only when the pull request affects the widget package or one of its verified build/release inputs.

An unrelated Admin, backend or documentation pull request must not display an Assistant widget check.

The existing PR 12F implementation reduced execution cost but retained the widget job on every PR.

For an unrelated PR, GitHub currently shows:

Assistant widget ✓

even though these steps are skipped:

checkout
npm ci
Changeset validation
lint
test
build
pack verification

That status is misleading because a reviewer can reasonably interpret a green Assistant widget check as evidence that the widget was successfully validated.

PR 12G must change the CI boundary so:

check present = widget validation actually ran

and:

check absent = PR cannot affect the widget

Current architecture

The general .github/workflows/test.yml runs on every pull request to main.

It currently contains:

jobs:
assistant-widget:
name: Assistant widget

The job runs a path-filter step first.

For unrelated PRs, the path filter reports that the widget is unaffected, after which all expensive validation steps are skipped.

The job itself nevertheless completes successfully, producing a green:

Assistant widget

check.

This satisfies global required-check semantics but creates a misleading PR signal.

PR #81 proves the issue:

- the PR changes Admin functionality;
- widget-relevant paths are not changed;
- widget quality gates are skipped;
- GitHub still displays Assistant widget ✓.

The CI should instead model domain ownership directly through workflow trigger paths.

Required implementation

1. Move Assistant widget PR validation into a dedicated workflow

Create a dedicated workflow, preferably:

.github/workflows/test-assistant-widget.yml

or another repository-consistent descriptive name.

Use a clear workflow name such as:

name: Assistant widget

The workflow must own the Assistant widget PR checks.

Remove the Assistant widget job from the generic:

.github/workflows/test.yml

workflow.

Do not leave a detector or placeholder widget job in test.yml.

2. Use path-scoped pull-request triggering

Configure the dedicated workflow so pull_request execution occurs only when widget-relevant paths change.

At minimum inspect and consider:

on:
pull_request:
branches: - main
paths: - 'packages/assistant-widget/**' - '.changeset/**' - 'package.json' - 'package-lock.json' - '.github/workflows/test-assistant-widget.yml' - '.github/workflows/publish-assistant-widget.yml'

The final path list must reflect verified repository dependencies.

Do not blindly copy this list if repository inspection identifies additional shared widget dependencies.

Do not include:

apps/**
apps/admin/**
apps/backend/**
docs/**
.codex/tasks/\*\*
\*\*

unless a specific verified file within those areas actually affects the widget package.

3. Remove runtime relevance filtering

Once the workflow itself is correctly path-scoped, remove:

- dorny/paths-filter;
- Check for widget-relevant changes;
- steps.filter.outputs.affected;
- conditional if: expressions whose only purpose is deciding whether the widget is relevant.

The workflow trigger should determine whether the workflow exists for the PR.

Do not retain redundant runtime path detection.

4. Preserve the complete widget validation pipeline

When the dedicated workflow is triggered, it must actually run:

npm ci
npx changeset status --since=${{ github.event.pull_request.base.sha }}
npm run lint --workspace @redmoor/assistant-widget
npm run test --workspace @redmoor/assistant-widget
npm run build --workspace @redmoor/assistant-widget
npm run pack:verify --workspace @redmoor/assistant-widget

Use full Git history where required by Changesets:

uses: actions/checkout@v4
with:
fetch-depth: 0

Do not make any of these checks optional merely because the workflow is now path-scoped.

A fork using the same branch name must not receive this exemption.

The Release PR must still run:

7. Fix required-check configuration

This is mandatory.

If Assistant widget is globally configured as a required PR status check, path-scoping the workflow can cause unrelated PRs to wait indefinitely for a check that will never run.

Before completion:

- inspect the repository’s branch protection/ruleset configuration;
- determine whether the widget check is globally required;
- remove it as a universal required check if necessary;
- preserve appropriate protection for widget-affecting PRs where GitHub supports it.

The desired rule is:

Widget-affecting PR:
Assistant widget check runs and must pass.
Unrelated PR:
Assistant widget check does not exist and is not required.

Do not reintroduce a fake/no-op check solely to satisfy branch protection.

If GitHub cannot conditionally require the workflow under the repository’s current ruleset model, prefer not globally requiring the widget check rather than displaying misleading successful validation on every PR.

Other meaningful repository-wide checks may remain required.
